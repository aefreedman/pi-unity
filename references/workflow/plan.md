# Connected Planning and Documentation Routing

Use this overlay only after `engine.unity` matches the exact project copy. It supplements the shared Unity repository-research reference; do not repeat that repository search procedure here.

## Connected Inspection

If the standalone Unity CLI is available, use bounded machine-readable status and Pipeline discovery. A reachable Pipeline instance for this exact copy is a positive connected planning surface, not a busy-project failure. For a regular project-specific property or C# question, use `unity_pipeline_eval`, which rediscovers the exact copy and advertised `eval` immediately before dispatch. Use `unity_pipeline_inspect` for its package-owned purpose-built inspection commands when they provide better evidence. Do not use raw bash/Unity CLI dispatch. Never install or upgrade Pipeline, documentation, or packages merely for planning; do not open or close Unity, run tests, builds, imports, saves, package operations, or VCS/lifecycle actions.

Pipeline eval is bounded but arbitrary C# compiled by Roslyn and run on the Editor main thread. It is not expression-only or reliably statically read-only, so do not use a property allowlist or syntax classification as a security boundary. In planning, use it for the stated inspection question; mutations require explicit user authorization and remain outside ordinary planning scope. If CLI/Pipeline discovery times out, the Editor reloads or disconnects, identity changes, or output is malformed, report uncertainty and fall back to repository research rather than claiming absence or silently changing routes.

Lockfile or process presence is not a planning preflight failure. It remains relevant only to later launch tools: every GUI/batchmode route must retain exact process identity checks and a per-project launch mutex; direct Editor execution blocks native lockfiles, while Unity CLI may handle a proven stale lockfile only after no matching process is verified.
